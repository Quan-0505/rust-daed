# Rust daed 3.2.1 compatibility candidate

The candidate retains the pinned upstream UI `dc4af0e4d9e855e0d6ba6d719a2cc70f0be64327` and engine `f40c3494c7769efd796afff671d459db78f7ace9` documented in [UPSTREAM-20261016.md](UPSTREAM-20261016.md). The upstream repositories have no newer stable release than the pinned build as of 2026-10-18; this candidate is a device-compatibility update, not a claim of newer upstream code.

It adds an eBPF WAN-egress packet-layout check for ZTE F50 SIPA RAWIP. When the skb is IPv4 and its data contains a complete, length-consistent Ethernet+IPv4 frame, the program skips the Ethernet header before parsing the IP packet. Normal L3, malformed frames and IPv6 retain the zero offset. Unit tests cover valid frames, options, malformed lengths/version/IHL and IPv6. The patch hash is pinned in `upstream.json` and source CI applies it to the exact DaeNext commit before running tests.

It also repairs resident BPF LPM route-map population on E5. `BPF_MAP_UPDATE_BATCH` progress is preserved, and partial `ENOMEM` results continue with the unprocessed suffix; scalar insertion retries transient `ENOMEM` with bounded backoff. The patch hash is pinned and applied after the SIPA RAWIP compatibility patch. The installed ARM64 candidate passed 10 daemon service restarts and 3 OpenWrt soft reboots on the first E5, retaining 15 NodeBabyLink routes and restoring HTTPS successfully. One service restart needed several HTTPS probes over about 15 seconds before proxy egress recovered; control-plane commit and proxy egress readiness are checked separately.

F50 requires the daemon to use a veth network namespace; the integration must explicitly select veth and must not depend on Go-only environment variables. That firmware-side wiring and live F50 IPv4/IPv6 TCP/UDP checks remain required before calling the engine verified on hardware. E5 is a separate target: it must retain the existing internal `e5root` update path and its account/subscription migration must be proven before replacing the running Go engine.

The E5 evidence covers the installed ARM64 candidate on the first E5 and repeated live restarts. It does not validate the patch on F50 hardware. The F50 path still requires firmware-side veth wiring and live IPv4/IPv6 TCP/UDP checks. A complete release build and package verification are still required before publishing this candidate as a general release.
